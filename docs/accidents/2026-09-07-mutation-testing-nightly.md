# 复盘：变异测试为什么没当上 PR 门

| 字段 | 值 |
|---|---|
| 类型 | 设计复盘（非生产事故） |
| 日期 | 2026-09-06 引入夜跑，2026-09-07 补回退检测 |
| 相关 | decision-log「CI 门禁」、`.github/workflows/mutation-nightly.yml` |

## 做了什么决策

变异测试（gremlins 注入变异，跑受影响测试看杀不杀得掉）不走 PR 门，走夜跑：每天 cron 全量跑，维护基线，检测回退，回退自动开 Issue。

## 为什么这么选

最初的设计意图就是把变异测试挂进 PR 门——覆盖率只证明"测试跑过这行"，变异测试才证明"测试能抓住这行的错"，听着是质量门的完美补刀。

算了一笔账就退了：gremlins 每个变异点要重连库、重跑受影响的测试，单点是分钟级。一个 PR 动辄几十个变异点，当门意味着每个 PR 挂几小时等结果。门的作用是快速给确定性答案，分钟级 × 几十点的检查塞进门里，门本身就废了。

## 效果数据如何

- 2026-09-06：门禁拆两段式（PR 五道确定性检查 + main 上构建镜像），变异测试以夜跑形态进入 CI。
- 2026-09-07：夜跑补基线回退检测（metrics 分支记录基线，回退自动开 Issue），gremlins 钉版本。
- 变异测试不再阻塞 PR 反馈；变异数据照常积累。

## 踩了什么坑 / 教训

- **门禁也是资源**。进 PR 门的检查必须同时满足两条：确定性强（同样的输入同样的结果）、反馈在分钟级。两条缺一条，再高级的检查也只能去夜跑。
- 夜跑不是降级成摆设：没有基线和回退检测的夜跑等于不跑。09-07 补的就是这一半。
- 工具钉版本不是洁癖。变异工具、扫描工具（govulncheck 钉 v1.7.0）都不许浮动，否则红灯没法归因——是代码坏了还是工具变了？

## Follow-up

decision-log 留有活口："数据够了再议升格"。等夜跑积累出稳定的变异存活率基线、且单次运行时间压下来之后，重新评估是否把"变异存活率回退"提为 PR 门。
